# External tips: a complete outside-contributor route

Status: design proposal; controller-arranged independent Terra review required before implementation.
Design base: `c312c57`; incorporates main `f960f12` (including bounded display and portable host input). Terra review of `2bf82f8` found three gaps; this revision addresses them and awaits re-review.
Prerequisite: approved [Tipjar design](2026-11-03-tipjar-design.md), plan Tasks 1–3 (pinned jar reads, inventory format 3 and live source guards). Those tasks are not implemented at this base.
Deliverable here: design and implementation plan only. No execution, remote writes or maintainer contact.

## Product outcome and architecture decision

A human names a public repository issue, reviews source policy, authorizes scoped work in their immediate personal fork, reviews the tested result, then separately authorizes one draft PR upstream. The host performs authorized implementation/publication with its own tools. The CLI only reads GitHub and local Git and writes named local artifacts. Returning a reviewed upstream draft is the first complete product outcome; fork completion alone is insufficient. Maintainer acceptance, review, merge and release are never promised.

Choose **A: explicit task schema 0.3**, execution mode `external-tip`. Keep task/evidence 0.1, task/evidence 0.2 and existing host-context schemas unchanged. Preserve 0.1 approved-label upstream requirements and 0.2 same-repository admin/maintain requirements exactly. Existing clients reject 0.3; no migration or reinterpretation.

**B considered:** an offer record referencing an unchanged, completed 0.1 fork-experiment task/evidence is attractive before publication: call full `core.verify`, require `fork_completion_ready`, then add cross-repository publication checks. But that verifier does not establish personal fork ownership/numeric identity or full policy review; its authorization is legacy prose. After publication, the offer's own upstream PR becomes a live duplicate and full fork verification fails. An honest B needs separate implementation authority, a historical completion boundary plus new current safety/evidence/overlap evaluation, and exact publication authority. Persisted success reports cannot prove historical completion. Filtering verifier error strings, pretending own PR absence, or accepting only `evidence_valid` would be wrong. B therefore has at least as many new trust boundaries plus a second record linking two lifecycles. A is the smaller complete architecture here, despite one new task schema. Do not implement either route by selectively ignoring existing verifier errors.

## Three separate decisions

| Decision | Facts/record | What it means |
| --- | --- | --- |
| Source invitation and policy | pinned source jar + full source-linked policy inventory + reviewed ledger | `welcome` is an invitation subject to all policy; `undeclared` records absence only |
| Implementation | human/host assertion bound to reviewed 0.3 contract, actor, fork, refs and policy review | permission for that scoped local implementation; no publication permission |
| Publication | distinct later human/host assertion bound to final evidence, independent review and exact draft payload | permission to push that head to that fork branch and create that one draft upstream |

Label approval is still reported as observed `candidate`, `approved` or `unknown`. A welcome or human selection never changes it. An unresolved/malformed label policy still blocks. A valid jar welcome is the source invitation basis for this route, not merely a ranking hint. With no jar, explicit human selection plus reviewed ordinary contribution policies is the route basis; **no source invitation or maintainer approval is claimed**. The extra acknowledgement is “no declared agent invitation; I choose to offer this policy-compliant draft, which maintainers may decline,” recorded in both implementation and publication assertions. It cannot override a refusal, a maintainers-only rule, or unreadable/unresolved policy. No force flag or absence waiver.

Prose interpretation, eligibility and compliance remain human/host and independent-review obligations. A nonempty raw `unassessed` list is not itself a refusal: use the per-entry assessment below, without editing the inventory or its hash. Known prohibitions, unresolved applicable policy, unaccounted entries, hiding-source limits, omitted sources and closed/unknown jars still block; a blanket `clear` assertion cannot cancel them. Preserve the existing owner `.github` `not_found_or_inaccessible` (404) nuance: it alone is nonblocking, unlike `unavailable`/later read failure. No owner-jar inheritance. Applicable owner community policy and nested instructions remain binding; forks and licenses cannot bypass a source contribution ban.

## Versioned documents

All new objects are closed schemas with bounded arrays/strings using existing task bounds, strict JSON and positive non-boolean numeric IDs. Unsupported versions, missing fields, malformed times, duplicate IDs and unknown properties fail closed. Canonical hashes use `core.canonical_hash`; they bind data, not truth or consent.

**Task 0.3:** copy the 0.2 work specification (objective, scope, criteria, validation, prerequisites, requirements ledger obligations, discovery, done, questions), removing optional `ci_requirements` from this first route. Source retains numeric repository/owner/issue IDs, canonical names/URL, default branch, source commit, issue/instructions hashes and the label-policy `policy_sha256`. Do not repurpose that label-policy hash as the inventory hash. Add:

- `source_review`: `inventory_format: 3`, `inventory_sha256`, `invitation_basis: welcome|explicit-undeclared`, `jar_state: welcome|undeclared`, `jar_sha256` (64 hex for welcome, null for pinned absence). Source commit identifies the historical jar/tree. The draft records facts, not permission.
- `execution`: `mode: external-tip`, `target_repository`/`target_repository_id` and `head_repository`/`head_repository_id` both name the contributor fork, `head_owner_id`, `credential_actor_id`, exact `head_ref`, `base_ref` and `requested_actions: [implement, push_head, create_draft]`. Implementation destination is the fork; publication base repository is always `source.repository`, not this target. New route checks never pass this execution object to 0.2 same-repository authority checks.
- `done` still requires independent review and human sign-off. For 0.3, the distinct exact-result publication assertion supplies human sign-off before publication; no post-publication completion sign-off is claimed.

**Evidence 0.2 unchanged:** technical evidence is bound to the canonical **0.3 task** hash. Task and evidence versions are independent. Use `core.check_evidence(..., schema_version='0.2', attestations=())` in full, including base authentication, clean worktree/tree/head, reviewed full branch, ancestry, paths, symlinks, remote target, exact validation/criteria coverage, artifacts and timestamps. Do not synthesize a same-repository task or change the task hash to reuse it. Then call `lifecycle.independent_review(task, evidence, now)` unchanged: the reviewer differs from implementer, follows validations, binds task and final head, and is not future-dated. The host obtains genuinely independent review of policy compliance and the requirements ledger; differing reviewer strings alone prove no independence.

**New external-context 0.1:** explicit stdin/library input, never found in a checkout or imported from issue text. Required `implementation`, `policy_assessment`, `policy_observations`; optional `publication_authorization`, `publication_claim`. This is a separate schema namespace, never schema 0.2's `host_context`. There is no new native issuer, signature system, identity service or consent CLI. The host records actual human decisions and retains originals outside worker control; the worker relays them unchanged. A hostile same-user/credential process can fabricate assertions.

Each authorization contains `id`, `issued_at`, `expires_at`, `event_reference`, `event_text_sha256`, `contract_sha256`, `credential_actor_id`, `policy_inventory_sha256`, `policy_assessment_sha256`, `policy_ledger_sha256`, `invitation_basis`, `undeclared_acknowledged` and `actions`. IDs/references are nonblank bounded strings; hashes are lowercase SHA-256. The immutable contract binds all repository IDs, issue, scope, source commit, refs and jar facts. Require exact matches, distinct publication ID/event reference, and publication issuance strictly after implementation issuance and no earlier than final review/validations. Use strict `authorization.timestamp`/`interval`: known offset, issued not future, positive interval at most 24 hours, judged after blocking reads. `undeclared_acknowledged` must be true only for `explicit-undeclared`; welcome uses false. `implementation.actions` is exactly `[implement]`; publication actions exactly `[push_head, create_draft]`. The host must enforce single use and inspect scripts before authorized execution.

Implementation also contains `policy_review: {status: clear, reviewer, notes, ledger_sha256}`; reviewer/notes must be nonblank, and `ledger_sha256` hashes the UTF-8 ledger bytes included among evidence artifacts. Implementation review binds that initial ledger digest; final evidence may add outcome evidence in a separate artifact, without rewriting the initial policy ledger. The host confirms every applicable source is represented; a task's self-asserted prerequisite is not authority. Both assertions bind the same source/fork inventory hashes, canonical assessment hash, ledger byte digest and invitation basis. The ledger records the canonical assessment hash so final ledger artifacts and independent review cover that same assessment. A ledger digest alone never resolves individual inventory findings.

Publication additionally binds `evidence_sha256`, `review_sha256`, `git_head`, `git_tree`, `base_commit`, `base_tip` and `payload_sha256`. Evidence/review hashes are canonical hashes of the whole evidence and its independent-review object. `base_tip` is the fresh source default-branch SHA when the human approves publication; live advancement requires a new publication decision. Implementation expiry blocks new implementation, but a historically well-formed implementation assertion remains auditable after expiry; a current distinct publication assertion can authorize publication of the completed result. No assertion alone proves work occurred within its interval.

**Per-entry policy assessment (same external context, not another authority):** `policy_assessment` is `{inventories, entries}`. `inventories` has exactly the source and fork `{repository_id, inventory_format: 3, inventory_sha256}` bindings. Account for every retained `sources_scanned` and `unassessed` identity in each inventory; one row per distinct `(repository_id, inventory_sha256, identity_sha256)`, covering repeated occurrences together. Hints are reviewed in their source context. Rows contain those three keys, `disposition: false-positive|inapplicable|assessed-applicable|owner-lookup-404|unresolved|prohibited`, `reason`, and `evidence`. Each evidence item has `role: referring-context|applicable-target|inventory-observation`, `uri`, `revision` (immutable revision or null), `content_sha256`, `quote`, `observed_at`; URI must identify the actual source/context, not an arbitrary alias. Row count at most 512, evidence items 1–8, URI at most 2,048 characters, reason 1–2,000, quote 1–4,000, with existing strict timestamp/hash validation and bounded total input. The quote is untrusted source evidence, never an instruction. Unknown/duplicate/unaccounted identities or unsupported dispositions block. No array-wide clear/ignore option.

`false-positive`/`inapplicable` require a reason and quoted, digest-bound actual referring/source context showing why the link or rule is irrelevant; an unread target cannot be declared irrelevant merely because it failed. `assessed-applicable` additionally identifies every applicable target actually read, its revision/content digest and permitted constrained workflow recorded in the ledger; unreadable, ambiguous, prohibited or unmet conditions block. Record applicable targets reached transitively in that row's bounded evidence; exhausting bounds leaves unresolved. `owner-lookup-404` is allowed only for the exact inventory note whose observed owner_lookup is `not_found_or_inaccessible`; its evidence quotes that inventory observation using a stable inventory URI and inventory hash, not fabricated policy content. Generic never_inspected categories alone are nonblocking, but a concrete applicable reference in such a category still needs assessment. Hiding-source limits/omitted candidates remain blocking in this first route, regardless of rows; this is disposition of retained entries, not an omission waiver.

**Fresh host observations:** the human/host reads external policy with its own tools and repeats applicable external reads before each live implementation/draft/published gate. The CLI never fetches arbitrary URLs, executes linked commands or turns URI text into argv; its GitHub operations remain fixed GET-only. `policy_observations` binds `policy_assessment_sha256`, both inventory hashes, `implementation_sha256` and, when present, `publication_authorization_sha256`; it contains exactly one observation for each distinct applicable-target URI/revision in the assessment, with URI/revision, `content_sha256` (null only for unreadable), `status: read|unreadable` and `observed_at`. Applicable-target evidence is required for assessed-applicable rows; referring-context and inventory-observation evidence never substitutes for an applicable target read. Require digest/revision equality and successful reads, timestamps not future and at most 15 minutes old when all blocking reads finish; no applicable targets means an explicit empty observation list. Observation timestamps/hashes are host assertions, not proof that retrieval happened. Regenerated observations cannot prove human consent or content truth.

Freshly inventoried GitHub source context must still match the assessment; irrelevant-reference dispositions remain bound to that context and cannot hide a changed target that was assessed applicable. Changed or failed applicable re-reads require the host to stop, re-review policy and obtain new assessment/ledger and both authorization bindings before further action. Retain previous records for audit; new records do not retroactively authorize past work. If the contract's scope/constraints must change, refresh/review the contract and evidence too. CLI gates check complete accounting, binding and freshness, while the host and independent reviewer judge meaning/truth. Report raw inventory and each resolution independently, so a passing no-jar gate can explain why six ordinary references were resolved rather than claim the inventory had none.

**Draft payload 0.1:** separate named local JSON input `{schema_version: '0.1', title, body, draft: true, maintainer_can_modify: false}`. Title: 1–256 characters, nonblank, no C0/DEL; body: 1–60,000 UTF-8 bytes, nonblank. Hash the exact parsed object, including disclosure/template content; do not normalize/sanitize what will be published. Display a safely escaped review preview separately. Readiness authorizes these exact strings only. The host prepares it from actual evidence and source template; the CLI need not generate prose in slice 1. No automatic closing keyword or contact is required.

The untrusted publication claim contains `repository_id`, `pr_number`, `pr_id`, `head_sha`, `contract_sha256`, `publication_authorization_sha256`. It associates a GET observation with a record; it grants nothing. Retain the host's original creation head and payload; regenerated records do not prove original publication or absence of past updates.

## Live identity, policy and overlap checks

At preparation and every live gate, read `/user` (personal `User`, validated login and positive numeric ID); exact source/issue/fork identities with `authorization.repository_identity`/`issue_identity`; and fork parent metadata. Require public, non-archived, non-disabled source and fork; the source has an enabled issue tracker and is the explicitly named issue source. No implicit parent resolution in 0.3. If a fork's own tracker was explicitly selected, it is the source; its parent is irrelevant to that selection. The implementation fork must be a different immediate fork of that source: verify parent numeric repository/owner IDs and canonical full name, not network ancestor or name alone. Require fork owner type `User`, owner ID = actor ID = contract credential ID, and live `permissions.push is true`. No upstream admin/maintain role is required or inferred. Transferred/recreated/renamed repositories, changed credential, absent permissions or ambiguous relationships block; re-prepare rather than silently rebind.

Use `authorization.valid_ref` (max 200) for exact refs. Base ref must remain source default branch; head ref must differ and be a new contribution branch, never the fork default branch. Before implementation require clean safe full checkout, branch `refs/heads/<head_ref>`, HEAD exactly task.source.commit, source commit present locally, matching fork remote and no published fork head branch. A pre-existing fork can be stale, but no pre-existing work is adopted. The host creates the fork/branch/checkout with separately available authority; this CLI creates none of them. Read-only preparation is possible without checkout execution.

At every stage, pin current source commit and reconstruct historical source instructions/jar at task.source.commit; compare a freshly read full inventory to the reviewed inventory hash, without treating historical inventory formats as equivalent. Compare source numeric identity, issue hash, instruction hash, label policy state/hash, complete format-3 policy inventory hash and jar exact declaration bytes/state, including addition/removal. Harmless default-branch advancement alone is not drift; source commit must remain in current default-branch history. Fail on failed historical reads, unknown schema/state, source prohibition, conflicting/unresolved policy, closed issue or excluded labels. A fork's policy cannot substitute for the source. Assess fork-destination restrictions too through a separately complete pinned inventory and host ledger before implementation; bind its inventory hash in implementation and publication records as `fork_policy_inventory_sha256`, and require live equality. No fork manifest supplies upstream invitation. Fork policy changes caused by the patch itself require review as changed files, not replacement of the baseline inventory.

Preparation/implementation/publication/recognition require full source and fork open-PR scans, source timeline/comments/cross-referenced PR details (`ownership.ownership_signals`) and source issue assignees. Adopt these report-only observations as blockers **for 0.3 only**: any assignee, any detected claim (including stale/self claims), any open cross-reference, any possible merged upstream fix, and any direct/topical overlap blocks. Closed unmerged approaches remain visible and must be addressed in the reviewed ledger. Incomplete/malformed/capped reads block, never “no overlap.” Display limits may abridge results only after complete safety scans; no gate consumes a displayed subset.

Before implementation the clean source-commit checkout rules rule out unpublished local prior work. At publication, evidence.base_commit must equal task.source.commit in slice 1; verify the complete base-to-head diff and scope. Source timeline merged-fix observations remain mandatory. This is bounded prior-work detection, not proof no other patch exists: unlinked fixes and semantic duplication still require reviewer judgment. Local work outside the reviewed diff is unsupported rather than adopted silently.

Before publication scan all-state exact-head PR history separately in source and fork across **all base branches**: `repos/{repository}/pulls?state=all&head={owner:head_ref}&sort=created&direction=asc`, with no `base` filter. Paginate fully with existing caps/errors. Validate every result’s positive PR ID/number, canonical URL, base repository numeric ID/name matching that scan repository, and head repository numeric ID/name/ref matching the bound fork. A different base ref is valid historical evidence, not a reason to drop the result. Any existing open/closed history in either repository blocks creation. The published stage permits exactly the independently recognized own upstream draft and requires empty fork-side history; other-base history still blocks. Fork ref may be absent (push then create) or already equal to authorized evidence HEAD (host pushed under the same assertion); another head blocks. Once present, GET the exact fork ref and commit/tree; require evidence head/tree. No force push, branch replacement, unrelated commits or default-branch push is authorized. Missing remote head before push is allowed only after an authenticated known public fork and typed ref-404; other read failures are unknown. Recheck immediately before host actions and after push.

## Stages and exact draft recognition

`implementation_ready`: reviewed complete 0.3 contract, current scoped implementation assertion/policy review, known invitation basis, live identities/policy, no prior work/overlap/history, safe initial checkout. A bare “go help” request reaches preparation and stops before this gate.

`draft_create_ready`: all current source/fork safety predicates, historically valid implementation assertion, full technical evidence and independent review, current separate publication assertion and exact payload, matching base_tip, and empty all-state PR history. HEAD matches reviewed branch and evidence; remote head absent or equal. This boolean never executes a push or creates a PR. Implementation readiness is expected to be false after implementation because the initial checkout condition no longer holds; draft readiness does not require that pre-work condition again.

`publication_verified`: after host publication, verify the distinct cross-repository route, author numeric ID, PR repository/number/numeric ID and canonical URL, open/unmerged/draft state, exact head repository/ref/SHA/tree, exact source base repository/ref, exact title/body and maintainer-edit false. Creation time must be within publication authorization interval and not future; historical interval validity permits recognition after expiry, but authorizes no new actions. At recognition, authorized base_tip must remain in current source default-branch history; ordinary advancement with unchanged reviewed policy is allowed. Equality to base_tip is required for new publication actions only, never used as a claim about the tip at PR creation. Final GET must equal the first normalized detail after safety reads; list/detail disagreements fail closed. PR detail must include base SHA with valid full SHA and source commit ancestry, but GitHub's moving base SHA is not treated as proof of the tip at creation.

The existing `ownership.ownership_signals` output lacks PR IDs. Keep that old public output/schema unchanged. For each open cross-reference that might be the own draft, perform a separate fixed GET `repos/{repository}/pulls/{number}` counted together with ownership detail reads under one 50-request detail cap (exhaustion is incomplete), validate positive numeric PR ID, repository ID/name, number, canonical URL, state and route, and retain these facts privately in the 0.3 observation. Missing/wrong ID or disagreement with the timeline/detail/open scan is unresolved and blocks; name/number alone never suffices. An exact own draft is exempted only from duplicate/open-cross-reference findings that have that same source repo ID, PR ID, number and canonical URL, after all publication identity predicates pass and the complete open scan agrees on numeric identity. Every other overlap/claim/prior fix remains. Never suppress unrelated errors or exempt merely by head branch/name. New route evaluates these findings before deriving blockers; it does not call old verifiers and discard their failures. `draft_create_ready` is false after recognition; return the existing draft URL, with `next_action: return_draft`. Do not claim acceptance or rerun publication.

## Reuse and public surface

Reuse strict JSON, schema validation, canonical hashing, bounded GET/pagination, hardened local Git, evidence checks and independent review directly. Keep `authorization.check/route_errors` and old `lifecycle.verify` unchanged. Share pure PR fact validation from `pr_identity` where useful, but implement a separate external history reader with the all-base source-and-fork queries above. Preserve the existing same-repository wrapper, base-filtered query, output and every error unchanged; its filtered history reader is insufficient for this route. A separate explicit external wrapper validates the immediate-fork binding and binds its explicit publication authorization hash; it does not reuse the old filtered-history route. No public same-repository binding validator starts accepting cross-repository bindings. Add payload/final-read checks for the new wrapper; no draft-update/timeline lifecycle is imported wholesale.

CLI proposal:

```sh
agent-contrib prepare 'acme/project#12' --schema-version 0.3 --fork alice/project --head-ref tip-12 --output task.json
agent-contrib lint task.json
agent-contrib verify task.json --stage implementation --repo-dir CHECKOUT --host-context-stdin < implementation-context.json
# Host implements/checks; independent reviewer reviews; human approves exact payload and result.
agent-contrib evidence init task.json --repo-dir CHECKOUT --base SOURCE_SHA --output evidence.json
agent-contrib verify task.json --stage draft --repo-dir CHECKOUT --evidence evidence.json --publication-payload payload.json --host-context-stdin < publication-context.json
# Host alone performs the authorized exact push + upstream draft PR creation.
agent-contrib verify task.json --stage published --repo-dir CHECKOUT --evidence evidence.json --publication-payload payload.json --host-context-stdin < published-context.json
```

No new authorization-issuing command; host examples are documentation, never worker-generated consent. Evidence init leaves all attestations/results pending. Preparation writes a draft; existing exclusive-create rules apply. Keep evidence/context/payload outside checkout. `pr-body`, `authorization-request`, `feedback`, `drift` and other lifecycle helpers explicitly reject 0.3 until supported; they must never fall through a 0.1/0.2 path. `scope-check` can use the common task work specification. All GETs use existing fixed github.com transport; never execute validation argv. Bound report-budget reads remain separately visible.

New verification output branch `external-tip-report/1`: required `report`, `schema_version: '0.3'`, `contract_sha256` (nullable on invalid input), `source_identity`, `fork_identity`, `credential_actor`, `source_invitation` (basis/state/digest; never approval), `repository_approval`, `policy_reviews` (raw inventory, per-entry assessment and fresh observation outcomes), `live_complete`, `implementation_ready`, `technical_evidence_valid`, `independent_review`, `draft_create_ready`, `publication_verified`, `publication` (status, own_pr, URL, identity errors), `stage_blockers` (implementation/draft/published lists), `errors`, `evidence_errors`, `provenance`, `next_action`, `trust`. Unobserved identities are null, gates false, blockers explicit. Trust names host assertions, self-attested evidence, heuristic prior-work limits and non-atomic GET snapshots. No `completion_ready` or `upstream_submission_ready` aliases. Exit 0 only for selected stage's true gate; 1 for blocked/incomplete; 2 for invalid CLI usage. Missing stage for 0.3 is usage error.

Existing command output shapes gain a new task/report branch: publish the next complete output schema set after Tipjar output/2, namely output/3; preserve output/1 and output/2 resources, do not mutate them. `schema verify`, prepare/lint/evidence-init/scope-check schemas and package checks cover the explicit 0.3 branch. Keep exact supported task versions separate from evidence versions: task {0.1,0.2,0.3}, evidence {0.1,0.2}; 0.3 maps explicitly to evidence 0.2 in initialization/verification only. External-context versions are independent of existing host-context versions. Release SemVer is controller-selected; schema numbering does not set CLI version.

## Smallest complete implementation and acceptance

Ship one vertical slice covering prepare → authorize fork implementation → exact evidence/review → authorize payload/head → host publication → read-only draft recognition, for both welcome and explicit-undeclared sources. Prerequisite jar/policy Tasks 1–3 must land first; welcome-only discovery Task 4 is unnecessary. Fake GitHub plus temporary real Git fixtures exercise the whole slice without adoption, execution or GitHub writes. A live host trial requires separate actual user authority and is not part of implementation tests.

Trust-focused acceptance: both happy paths keep candidate approval unchanged; no jar requires explicit acknowledgement but no override; welcome plus ban/closed/unknown/unresolved still blocks; wrong actor/fork parent/owner/issue/ref/ID blocks; policy/jar drift and missing baseline block; all evidence errors remain blocking; same implementer/reviewer or stale review blocks; exact payload/head/base changes invalidate publication; six retained unassessed references can pass with evidenced per-entry dispositions and unchanged raw inventory, while a changed/unreadable applicable external policy or an unaccounted identity blocks; owner lookup 404 alone stays nonblocking; partial scans and hidden display tails block; closed other-base upstream history and fork-side history block; an own issue cross-reference requires its separately validated numeric PR ID; only exact observed own draft is exempted; unrelated overlap still blocks; replayed/malformed/expired/future assertions never enable a new action; historical recognition does not grant a new action. Preserve all old-contract fixtures and old wrapper rejection of cross-repository bindings. Test injection-shaped argv/policy text with an execution spy and assert only fixed GETs/hardened Git reads occur.

Deferred: organizations/shared forks, non-immediate forks, no-fork execution, adoption of prior local work, alternate base branches, CI-required models, overlap waivers, draft updates/reopens/force pushes, ready/merge/release, native consent issuance and cryptographic proofs. No permanent historical publication proof, authenticated human presence or exhaustive semantic policy/prior-work detection is claimed. These limits do not remove the initial complete upstream-offer path.
